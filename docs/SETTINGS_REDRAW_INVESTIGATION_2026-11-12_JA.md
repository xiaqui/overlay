# 設定変更時の角丸・ナビバー再描画／画面スクロール挙動の調査タスク（2026-11-12）

状態: **調査・TODO登録のみ。実装、merge、ビルド、APK配送は未承認・未実施。** 最新 `main` を基準に行った静的調査結果。Z3TC実機での発生頻度・画素・バージョン差は社長が並行して検収する。再現未確定の仮説は断定しない。

## 背景・報告

社長報告: PR #29（設定画面整理）や後続PR #32（診断追加）以後、設定変更のたびに角丸やナビゲーションバーが消えて描き直されるように見える。PR #26 版 `0.7.0-battery-finish`（versionCode 7）との比較を実施予定。上部バー同色不具合とは別課題であり、未マージPR #35「Z3TC上部バー可視性と設定順の修正指示」と同じコード・TASKを同時編集しない。

## コード調査で確認できた事実

1. `OverlayService.kt` の `OnSharedPreferenceChangeListener` は `diagnostic` 以外の**すべての変更キー**で `lastQuery=0; rebuild()` を呼ぶ。これは PR #26 の merge `f8ee341f...` にも存在し、**PR #29で新規導入された動作ではない**。
2. `rebuild()` → `clearWindows()` は `navbarLayer?.clear()`、`statusbarLayer?.clear()`、登録WindowManagerビューの `removeViewImmediate`、窓とキャッシュ/観測状態の破棄を行い、再attachする。時計・電池だけの変更でも角丸/ナビバー窓が一度消えうる。これは**実際に全ウィンドウ再構築を発火するコード経路**である。ただし視認できる点滅の再現／回数は実機未検証。
3. PR #29 の `MainActivity.toggle()` は `settings.set(key,value);showSettings()` に変更された。各 `choice()` でも保存→`showSettings()`。 `showSettings()` は `content` と `ScrollView` を作り直し `setContentView(next)`、前 `scroll.scrollY` を読み `next.post { scrollTo(0,y) }` で復元する。これは**設定Activity側の全体再生成／スクロール復元**であり、Overlayのウィンドウ `clearWindows()` とは別系統。PR #26 には同じスイッチ後の `showSettings()` はなかった。
4. PR #32 では時計配置の `settings.set("clock_left",...)` → `settings.set("clock",true)`、電池配置の `setBatteryDirection(...)` → `settings.set("battery",true)` と**複数保存操作**を導入。`Settings.setBatteryDirection` 自体も一つのEditorで `battery_direction` と `battery_reversed` の2キーを更新する。キー通知ごとに `rebuild()` が走るため、1 UI操作で複数回窓の全撤去が発生する可能性がある。実際の通知数は対象端末で計測し、同値の通知も確認する。
5. `MainActivity.onResume()` は表示ON時に `OverlayService.start(this)` を呼び、サービスの `onStartCommand()` は `rebuild()`。設定画面への復帰・プレビュー終了・権限画面復帰時にも独立した再構築要因となる。これもPR #26時点に存在したことを明記する。
6. スライダーはユーザー操作中の `onProgressChanged` では保存せず、`onStopTrackingTouch` で一度 `settings.set` する。したがって連続ドラッグ中毎フレーム再構築するとは現行コードからいえない。

## 目的と原因切り分け

**(A) 角丸・ナビバーなどOverlayレイヤーが消えて再出現する現象**と**(B) 設定画面自体の再生成／スクロールジャンプ・ちらつき**を別々に評価。PR #26(0.7.0)／#29(0.8.0)／#32(0.9.0)で、同じ設定操作が実際にサービス `rebuild` を何回発生させるか、WindowManager窓の remove/add が何回起こるか、設定画面の setContentView 回数とスクロール位置復元がどう変わったかを比較。旧版に同じ根本原因がある場合は「#29による新規退行」と断定しない。

### 調査・実装時の手順（実施は別途明示指示後）

1. 最新 main と未マージPR（特に #35）の状況を再確認し、実機試験結果を取り込む。設定一覧/スイッチ、選択ダイアログ、スライダー終了、アプリ別設定、権限往復、プレビュー帰還、表示開始／停止それぞれを対象に、**設定変更キー、listener呼び出し回数、rebuild実行回数、clearWindows、ナビ/上部/角丸のremove/add回数、設定ActivityのshowSettings/scrollY**を調べる。ログを新たに追加するときはデバッグ限定・個人情報非記録、出力・採取時間を絞る。
2. **原因候補を優先して検証**: (a) 不要なキーによる全窓再構築、(b) 一つの操作で複数 `SharedPreferences` 通知、(c) onResume/start重複、(d) Activity全面再構成とスクロール復元。変更イベント、実ウィンドウ再生成、画面上のちらつきとの因果を分ける。
3. 必要な場合の修正方針は `rebuild()` の無条件発火を避け、保存キーと影響箇所に応じて、既存Viewへの `invalidate/requestLayout/updateViewLayout` やBar再評価を利用する。窓タイプ・表示要素数・重ね合わせ方式・権限など**再attachが本当に必要な変更だけ全再構築**する。固定色/自動推定・上下同色・Recents・角丸例外・全画面例外・時計/電池の配置と移行に退行を出さない。
4. 1 UI操作で複数の設定を変える場合、同値の不要writeを避け、必要なら一括トランザクション／通知集約の安全な仕組みを選ぶ。間に半端な状態でサービス再構築が走ることも防ぐ。設定保存スキーマの変更・消失禁止。
5. `MainActivity` は変更項目に応じた局所更新を優先する。従属項目の表示/非表示や状態・ラベル更新を維持しつつ、無用な `setContentView`・強制 `scrollTo` を減らす。ユーザー操作後のスクロール位置・フォーカス・調整スライダーの値・ダイアログの選択状態を守る。全面再生成が必要な場合のみ、既存の位置保存を適用する。
6. Android 6〜10の自動試験で「無関係な設定を変更しても角丸/ナビレイヤーが不必要に破棄されない」「必要な場合は正しく再attach」「ON/OFFや方向変更時に確実に描画更新」「スクロール維持」を確認。実機でちらつきの見え方、OS時計・ナビボタンとタッチ透過、常駐PSS/CPUへの影響を検収する。旧版比較時にデータ削除や非互換ダウングレードを伴わせない。
7. 実機確認後に必要なら独立実装PRを作る。既存CI/署名/Drive固定ID配送作法は同repoの現行仕様に従う。現在は修正実装を開始しない。
